## Runtime boundaries

```text
Next.js / React workspace
  | HTTP + SSE + WebSocket
  v
FastAPI: identity + scoped domain services
  |              |                |
PostgreSQL   mounted disk   upstream adapters
  |                         /      \
change log + SSE        LikeC4   pi-host
```

| Component | Authority / lifecycle |
| --- | --- |
| Frontend | Workspace tabs, feature state, API clients. Use server-issued paths, never browser filesystem authority. |
| FastAPI | Identity, per-user storage, filesystem access, integrations. Keep routes at HTTP/WebSocket boundaries and reuse domain services. Store and file IO blocks, so a handler that calls it is a plain `def` (FastAPI's threadpool) or moves the call into `asyncio.to_thread`; a blocking call inside `async def` stalls every request and SSE stream (`tests/test_route_concurrency.py`). |
| Startup | Reap host processes an earlier backend left behind (see Host processes), sync Pi's `ollama` provider in an executor thread, apply database migrations, start extraction and change brokers. The `openai` SDK (about 0.5 s of import) loads on the first model call inside `lib/completions.py`, and GPT-Researcher on the first research run. A module-level import of either brings the delay into startup, `python -X importtime -c "import backend.server"` shows it. Shutdown closes clients/pool, stops workers, MinerU children and the Jupyter Server, then whatever host processes the backend's children left running. |
| LikeC4 | Stateless model parsing and syntax-tree operations. Backend launcher starts/stops it and waits for health before FastAPI. Architecture routes return 503 if unavailable, but managed launch fails when startup health fails and tears down/restarts both processes if LikeC4 exits. |

| --- | --- | --- |

| FastAPI | `127.0.0.1:8001` | `127.0.0.1:8002` |
| LikeC4 | `127.0.0.1:8011` | `127.0.0.1:8012` |

- `TransferMiddleware` (`backend/http_plumbing.py`) handles every whole `200` JSON/text body without its own `ETag` or encoding: GET gets a weak body-hash `ETag` with `private, no-cache`, so an unchanged reread answers `304` without the body; bodies of 1 KiB and up are gzipped (level 1) for clients that accept it. Bodies over 256 KiB hash/compress in a thread. SSE, streamed proxies, files, ranges and routes with their own validator (`/fileviewer/raw`) pass through. A 304 still runs the handler, it saves transfer, not server work.
- The same middleware inflates `Content-Encoding: gzip` request bodies before any route reads them (400 for a corrupt body, 413 past 512 MiB inflated). `lib/backend/api/http.ts` `jsonInit` gzips JSON bodies of 64 KiB and up with `CompressionStream`, so a long chat's save, which resends every message, uploads about a quarter of its bytes. Browsers without `CompressionStream` send the body as is.

### Host processes

Every long-lived process the backend starts ends with it, also when the backend dies without its shutdown (`kill -9` of a hung worker, a crash, a reload that kills the worker):

| Process | Ends with the backend through |
| --- | --- |
| Jupyter Server | A thread of its bootstrap (`jupyter._BOOTSTRAP`) watches its parent (the Jupyter service), stops the server like SIGTERM (kernels shut down) and exits after 10 s if that hangs |
| Kernels | The Linux parent-death signal set at launch: SIGKILL whenever the server ends, also by `kill -9`. ipykernel's own parent check misses a server that died while the kernel started |
| Neovim | PTY hangup when the backend's side of the terminal closes, the `nvim --embed` server ends with its TUI |
| MinerU `LocalAPIServer` | The library's stdin EOF watcher (`MINERU_API_SHUTDOWN_ON_STDIN_EOF`) |

- `lib/process_owner.py` is the net under these. The Jupyter Server and Neovim get `GIGACHAD_PROCESS_OWNER=<pid>:<start time>` of the process that started them (the Jupyter service, a backend worker) in their environment (`owned_environment`), kernels, language servers and whatever they run inherit it. Startup `reap_orphans` SIGKILLs every process of the user whose mark names a process that no longer runs (a pid that now runs another process counts as ended), so a hung server or Neovim a killed owner left behind ends with the next backend start. Shutdown `stop_owned` SIGKILLs what still carries the process's own mark (the service after `jupyter.shutdown()`, a worker for a language server Neovim left starting). Neither touches the caller or its ancestors. Both read `/proc`, elsewhere they find nothing
- A tab has a working directory (`contexts/tabWorkingDirectory.ts`): the surface it shows claims it with `useTabWorkingDirectory` (Pi session cwd, factory task worktree or repo, workbench file or project folder) and `tabWorkingDirectory(tabId)` reads it. The shell sends it as `cwd` in its `open` frame, the backend uses it when it is an existing absolute directory, else the home directory. A running shell keeps the directory it started in.
- Shell terminals (`routes/terminal.py`) are not marked: their hangup ends the shell and its plain jobs, programs the user detached keep running

## Frontend read recovery

- `contexts/StartupReadContext.tsx` bounds initial settings, models, prompts, projects, histories, sidebar listings and reasoning levels reads to 15 seconds.
- Report failures in a shared banner. Retry only failed reads without remounting the workspace or clearing drafts and loaded data.
- Abort timed-out or disposed requests and ignore obsolete responses. Do not add automatic retries to these startup reads.
- Keep streams, uploads, writes, and explicit post-mutation refreshes unchanged.
- `ProjectProvider` keeps the project list's identity when a refresh returns it unchanged, so startup refreshes (change-feed replay, first branch metadata) do not re-render consumers keyed on it.
- Every tab stays mounted and renders its own sidebar and chat, so a user-global value in tab-local state is fetched and held once per tab and the copies drift. Such values are shared resources: `lib/resource.ts` (one cached value, one request for all callers), instances in `lib/backend/resources.ts`, hooks in `hooks/useResource.ts` (the first read is a startup read). On it: models, prompts, reasoning levels per model, roots-enabled, provider usage, notes, each project's documents, all documents, the root tree, each mount's worktrees, template sets. A mutation `set`s its response or refreshes the resource, never a local copy.
- Freshness of the shared lists. Lists with change rows (notes, project documents, all documents) never read again on a tab switch: `watchDocumentLists`, mounted once in `AppShell`, invalidates them from the change feed, this device's own events included, and from the file events. Values without change rows revalidate when a tab becomes active (`revalidateOnActivation`, one request per value for all tabs): the root tree, worktree status, project lists that hold a LaTeX folder entry or architecture sources, and whatever failed its last re-read. Provider usage polls once in `AppShell`.
- `TabSidebar` (memoized) renders the sidebar beside the component that owns the tab's chat state, so a streamed token never re-renders navigation. Keep its props referentially stable. `memo` sits on the wrapper, not on `Sidebar`: React 19.2 kept stale `useEffectEvent` closures in a directly memoized component that only a context re-rendered.
- Startup reads only what the first view needs. The mounted-file picker reads `GET /api/fileroots/enabled` (no walk) once for all tabs at startup and lists every root's files (`/fileroots/files`) only when it opens: walking the roots in the startup burst competes with the sidebar tree and other reads for the backend's CPU.

## Identity and filesystem policy

- Keep production listeners on loopback behind trusted private Tailscale Serve. Prefer one private HTTPS origin for frontend and `/api`.
- Resolve `Tailscale-User-Login` to a database user. Serve strips client-supplied identity/capability headers. Directly exposing the backend would break this trust boundary.
- Grant host execution through `gigachad.local/cap/host`, carried in `Tailscale-App-Capabilities`. Missing/malformed grants do not grant host access.
- Development identity requires `GIGACHAD_ENV=development` and `GIGACHAD_DEV_USER`. That local login has host access.
- Treat `X-Device-Id` as a UUID for write attribution/echo suppression, never authorization. SSE may omit it.
- Resolve identity with one read per request. `resolve_user` writes only for a new login, a new or reassigned device, or a device last seen over `DEVICE_SEEN_INTERVAL` (one minute) ago, so concurrent requests never queue on the users row lock or a commit.
- Per-user display preferences are columns of `users` (`lib/user_preferences.py`): `animated_background` (default on) is returned by `GET /api/config`, set by `PUT /api/config/animated-background`, and switched in the settings menu. `AmbientBackdrop` draws nothing until the setting loaded and while it is off.
- Reject wildcard/empty production `GIGACHAD_CORS_ORIGINS`. Explicitly validate WebSocket origins too: CORS does not protect sockets.

| Operation | Policy |
| --- | --- |
| Pi sessions, factory, Neovim, workbench, LaTeX builds, learn mode, mounting/cloning roots, directory browser, redeploy | Require host access. A mounted root is readable in full, so mounting is a host action. |
| Ordinary file access | Restrict to that user's registered mounted roots and admitted linked worktrees |
| Host-access file content | Allow outside mounts only under the service user's home directory, retaining credential-store protection. Unreadable files return 403, not 500. |
| Git/tree/worktree endpoints | Require a mounted/admitted root. The host-gated factory task diff (`/api/factory/tasks/{id}/diff`) reads the task's workspace without a mount. |
| Credential files | Outside mounted roots, host access rejects `.ssh`, `.gnupg`, `.secrets`, `.aws`, `.azure`, `.kube`, `.docker`, `.password-store`, `.pki`, `.mozilla`, `.config/{gh,gcloud,google-chrome,chromium,BraveSoftware,op,rclone}`, `.local/share/keyrings`, token/history files (`.netrc`, `.git-credentials`, `.pgpass`, `.npmrc`, `.pypirc`, shell/psql/python history), `.env`, `.env.*`, app runtime `gigachad-bot/env`, and OMP `agent.db` / `models.yml`. Explicitly mounted roots remain admitted, so this is not a blanket denylist inside mounts. |
| Directory browser | Lists host directory names for host-access logins. Listing is not permission to read/write content. |
| File trees | Honor layered `.gitignore` rules and skip `.git`, `node_modules`, `.obsidian`, `.trash`. Explicit content paths still use access validation, not tree visibility. |
| Text decoding | Return 415 for non-UTF-8 content instead of lossy binary overwrite |

## Persistence and synchronization

| Data | Authoritative representation |
| --- | --- |
| Chats, prompts, project documents, memory, model configuration, sandbox records | User-scoped PostgreSQL logical namespaces through domain stores / `PostgresDataStore` |
| Uploads, PDF library, extracted Markdown/images | PostgreSQL asset records. PDF/MinerU files also have a convenience filesystem mirror. The only read back: `GET /api/assets/Mineru/images/<stem>/<name>` for a host-access login stores a missing image from `Documents/Mineru/images/<stem>/<name>` or the flat `Documents/Mineru/images/<name>` older extractions wrote (`attachment_materialize.restore_library_image`), so a database moved without the folders fills those images on first open. |
| Mounted file contents | Original disk files. Projects/attachments reference them rather than creating independently editable copies. |
| Architecture | Linked clone `docs/architecture/` when present, otherwise PostgreSQL `graph/<slug>/` |
| Diff notes/layout, per-device preferences, archived Code directories | Browser-local state, not shared database artifacts |
| Workbench documents | Disk files under `config.WORKBENCH` (`GIGACHAD_BASE_DIR/workbench`), referenced by absolute path from `project.json`, or a whole LaTeX project folder listed as one entry. Repo files stay where they are. Chat-to-Pi-session links: per-user JSON `workbench/chats.json`, read and written only through `lib/workbench/links.py` (absolute key or canvas key -> `{active, sessions}`, the key is a file or a LaTeX project folder). PDFs are never copied: a mounted PDF is read in place, a stored one from its library mirror in Documents. |
| PDF annotations | Canvas document `pdf-annotation/<sha256>.canvas`, keyed by the PDF bytes' SHA-256. `POST /api/fileviewer/annotations` creates it empty on first use. Every copy of the same bytes shares annotations, renames keep them, changed bytes start a fresh canvas. Strokes sync through the collaborative canvas path. |

- Keep logical namespaces independent of the physical Documents layout. Validate storage keys against absolute paths and traversal.
- Scope `PostgresDataStore`, assets, projects, file-root registry, and other domain dependencies to authenticated users.
- Check expected revisions on conditional writes. PostgreSQL `apply(writes, deletes)` is atomic: one stale revision aborts the whole batch, deletes included.
- Read several documents with `DataStore.read_many` (one query) instead of a read per key: project listings and prompt libraries depend on it. Content columns (`documents`, `assets`) are fetched in binary result format, half the bytes of hex text, and stored uncompressed out of line (`STORAGE EXTERNAL`, schema step `0011`), so a byte range fetches only the TOAST chunks it covers. Values written before `0011` keep their compression until rewritten.
- `documents.meta` (jsonb) holds chat tree metadata (`chat_id`, `parent_id`, `branch_message_idx`, `children`, `qa_count`). `ChatStore` writes it in the same statement as the content, stamped with the row version, every other write clears it. Branch metadata, the chat ID index and project cleanup read it with one `DataStore.list_meta` query, never chat bodies. Meta that is missing or stamped with an older version (code predating `0011`, project rename) is derived from the body and stored back by `write_meta`, guarded by the content hash, without a new revision or change row. Meta jsonb would not return unchanged (NUL, floats, unsorted object keys) stays NULL and is derived on every read.
- `documents.sha256` is a stored generated column (`sha256(content)`), so document hashes (PDF annotation keys) never read the content.
- Meta also carries `refs`, the keys an item references, for delete cleanup: a chat's attachments (each `vaultPath`, and `PDFs/<name>` for a PDF) written by `ChatStore`, a canvas's frame and attachment paths written by `CanvasMutationStore` with each accepted batch (other canvas writes leave it to be derived), a `project.json`'s `files` derived on read. Meta without `refs` (stored before it existed, or by older code after a rollback) counts as missing and is derived again, so no schema step backfills it. An annotation canvas's meta also keeps `hosts`, the host files it was opened with, which cannot be derived from content (see Delete cleanup).
- Keep development/production PostgreSQL containers and volumes separate. Their default Documents/PDF mirror is intentionally shared. Back up both database and mirror, not only code worktrees.
- Load user model defaults from persistent provider configuration. Seed shipped prompts only for an uninitialized collection, never overwrite an existing collection or restore deliberately deleted defaults. `get_prompt_store` checks each user's collection once per process, later prompt requests skip the check.
- Apply numbered `db/schema/` steps under a PostgreSQL advisory transaction lock. Record checksums in `applied_schema_steps`, reject modified applied steps, and apply pending steps in one transaction. Add migrations rather than rewriting applied history.

### Project rename and archive

- `ProjectStore.update_project` slugifies a new name. Same slug only renames, another slug runs `PostgresProjectRenamer` in one transaction; an existing destination raises `StorageConflictError`.
- The rename moves document and asset keys under `chat/`, `project/`, `graph/`, `memory/project/`, `attachment/project/`, rewrites slug/history fields and app-relative links inside JSON/`.md`/`.txt`/`.c4`/`.canvas`/`.snap` documents of app namespaces, and rewrites canvas mutation values. Prose, absolute disk paths and similarly named projects stay unchanged. Every move records change rows.
- A disk folder linked by the old slug's folder name stays linked through `linked_root` in `project.json`.
- Workbench folders cascade: `workbench.move_project_directories` moves each `WORKBENCH/<kind>/<old>` to `<new>` before the transaction (an existing non-empty destination refuses the rename as a conflict, an empty leftover is removed), and the transaction rewrites those absolute path prefixes in project file lists, `workbench/chats.json` (keys included), canvases and their mutation log and notes. A failed transaction moves the folders back. A crash between move and commit is not recovered.
- `archived` is a catalog flag (`PATCH /api/projects/{slug}`) that hides the project from the sidebar. Archiving Code directories is per device (`localStorage` `archived_code_directories`). Pi session archive/restore goes through pi-host (`/api/pi/*`).

### Project file names

- `project.json` `files` lists each referenced key as a plain string, or as `{"path", "name"}` when the project shows it under a display name. `ProjectStore` reads both forms and writes the object form only while a display name is set.
- Every read-modify-write of `project.json` (files, cards, tabs, learn sessions) goes through `ProjectStore._update_project`: it writes against the revision it read and rereads and reapplies on a conflict, up to 10 attempts (parallel uploads), then raises `StorageConflictError`.
- Renaming a file (`POST /api/documents/rename {slug, path, name}`, sidebar double-click renames the row in place: `FileTree` `rename`, `useInlineRename`) renames the file itself, keeping its suffixes unless the typed name already ends with the last one. An empty name, a separator, `.` and `..` are 400, a name in use is 409 (in its folder, or shown by another file of the same project, ignoring case), the same name is a no-op. The file name and every reference always agree (`ProjectStore.forget_file_names` drops the legacy display names of a renamed key).
  - Stored project file or note (`document_service.rename`): its key moves to the new name inside its own directory through the relocator below. Only notes and `project/<slug>/document/…` keys rename: library `PDFs/…` keys are 400 and the sidebar offers no rename for them, canvases and folders. A library copy `PDFs/<old>` of a stored PDF follows to `PDFs/<new>` (`follow_library_pdf`), MinerU re-extracts under the new name.
  - File on disk (`document_service.rename_on_disk`, an absolute path: workbench file or mounted file): `FileRoots.rename` renames it inside its folder under the same root and identity policy as a write (403 outside, 404 when missing or, in a project, not referenced, 409 when the target exists), then the relocator rewrites every absolute path reference and a failed rewrite moves the file back. The workbench `<stem>` folder keeps its name, it holds the document's folder. A `.tex` drops `.latex-build/<stem>.*` of both names (`latex.discard_build`), so a build never shows the old file's PDF.
  - LaTeX reference cascade (`_follow_in_tex_project`, `lib/latex_references.py`): after a disk rename inside a tex project, `rewrite_references(folder, old, new)` repoints the references to the file in the project's `.tex` and `.bib` files. The folder is the project folder, or the folder of the first root candidate when no root exists. Dot folders, `node_modules` and build output are not searched, and only a `.tex`, `.bib` or graphic can be referenced.
    - Commands: `\includegraphics`, `\input`, `\include`, `\includeonly`, `\bibliography`, `\addbibresource`, resolved against the project folder (not the referencing file's folder). The `% !TEX root` line resolves against its own file's folder. Commented-out text and every other byte stay.
    - A reference without extension stays without one while the extension is unchanged and no other format shadows it, else it names the new file in full. A `./` prefix stays.
    - Each rewritten file is recorded as a `document` change (`DiskFiles.record`) and returned as `changed` in the `POST /api/documents/rename` response. The frontend (`useFileRename`) calls `announceFileChange` for each, so open buffers merge the new text.
    - A failure in the cascade is logged and never undoes the rename, and a file that cannot be read, decoded or written is skipped. A rename stays inside one folder, so only references change, no file moves.
  - Open Neovim sessions, tabs and the Pi chat follow, see Workbench.
- `GET /api/documents` and `/all` return the display name as `name`, the project list returns each project's `file_names` (path to display name). The frontend resolves tabs, editor headers, canvas window titles and chat attachment chips through `useDisplayName` in `ProjectContext`, which every rename refreshes.
- Moving a canvas or stored file between projects or notes (`POST /api/documents/move`) keeps the name it is shown under: into a project as display name, into the notes as its key.
- Moves and renames run `PostgresKeyRelocator.relocate` (`project_rename.py`) in one transaction: every exact reference to the key (project file lists, chat attachments, canvases and their mutation log, app links in notes, `workbench/chats.json` keys and values) is rewritten, then the row is rekeyed. An absolute `old` (a disk rename) only rewrites references, no row exists to rekey. Change rows are recorded, a rename (same-directory move or disk rename) puts the new key in `changes.moved_to` of the old key's row (schema step 0014, also in the NOTIFY payload and the SSE event) so other devices move their tabs from the old to the new key. Every change names its `operation` (`write`, `move`, `delete`, schema step 0015, also in the NOTIFY and the SSE event), so a device tells a deleted resource from a rewritten one. Moving a stored file onto disk records a `move` for its old key, never a `delete`.
- Uploading a project file (`POST /api/documents/write-binary`, sidebar upload, canvas PDF export) stores it as `project/<slug>/document/<name>`. A PDF is also synced into the library (`PDFs/<name>`, Nextcloud mirror) and queued for MinerU, as `POST /api/fileroots/add-to-project` does for mounted PDFs (`attachments.sync_pdf`).
- Moving a stored project file to disk (`POST /api/documents/move-to-folder`, drag onto a Code folder) writes it into a file-root folder under the name it is shown under, never overwriting (409), then relocates every reference to the absolute path and deletes the stored row. From then on it is a mounted file: read from disk, never deleted by cleanup. A failed relocation removes the written file. A PDF is synced and queued as above. Canvases cannot move.
- Dropping mounted files or folders on a project (`POST /api/fileroots/add-to-project`) references them by absolute path, nothing is copied. A folder holding a root `.tex` (`latex.holds_root_document`) stays one folder entry, listed like a workbench LaTeX folder (`inode/directory` with its tree, images and `.sty` included), so a mounted LaTeX project joins a project and keeps living on disk. Any other folder expands to its PDF and UTF-8 text files. Removing the entry only unlinks it.
- Sidebar drags carry a kind (`FileTreeItem.dragKind`/`accepts`): stored project files drop only on project roots, `files` folders and Code folders, chats and canvases never on Code folders.

### Change delivery and canvases

```text
committed user write -> durable changes row -> PostgreSQL NOTIFY
  -> process ChangeBroker -> user-scoped SSE -> resource-specific refetch
```

- Resume `/api/sync/stream?since=<seq>` from the applied sequence. Subscribe before replay and suppress overlap to avoid missing concurrent commits. Replay (`changes.latest_changes`) sends only the latest change per resource, since clients reload by resource.
- A fresh page connects without `since`: the stream subscribes, then sends `event: cursor` with the user's head sequence (`changes.head_cursor`) and only later changes, no replay. `syncStream.syncCursorReady()` resolves on the first event, and startup reads (`useStartupRead`), file editors and the architecture view await it before reading, so a change racing a read still arrives as an event. A first connection that fails or sends nothing within 5 seconds releases the reads and reconnects with `since=0`.
- `UserScope.record` deletes the rows its new row supersedes (same user, kind and key) in the same statement, skipping rows another transaction holds (`FOR UPDATE SKIP LOCKED`), so the table keeps about one row per resource, deletes included. Replay from any cursor is unaffected, because it only ever returns each resource's latest row.
- Send metadata, not document contents. Bound subscriber queues, close lagging streams, and recover through durable replay.
- The stream also carries this device's own changes. `syncStream.subscribeToChanges` drops them, since a device already holds what it wrote, except for subscribers with `{ ownDevice: true }`. Only `watchDocumentLists` opts in: lists are derived from writes made anywhere in the app, so no writer has to refresh them.
- Keep `.canvas` snapshots in documents and accepted mutation batches in `canvas_mutations`.
- New and transformed ink points are stored at 0.01 units (x/y) and 0.001 pressure (`inkPoint`, `lib/drawing.ts`): capture, selection move/scale, duplicate and cross-canvas drop. Existing strokes keep their digits until transformed.
- Serialize canvas writers with a document row lock. Apply snapshot/log/change-row updates transactionally, deduplicate mutation IDs, and replay accepted batches by revision.
- Keep canvas editing undo separate from general resource deletion.
- **Canvas chat** (host access). An open canvas has a Pi chat in the tab's file panel (`FileChat` from `WorkspaceSurface`), the scratch canvas has none. `POST /api/workbench/prepare` answers a stored `.canvas` key unchanged (404 when missing) and an absolute `.canvas` path in place, sessions run in `WORKBENCH/canvas` with the canvas prompt and see the canvas only through screenshots. Its sessions are linked under the canvas key in `workbench/chats.json`, which key relocation rewrites on rename and move. A screenshot (`useCanvasScreenshot`) still goes to the clipboard and is handed to `CanvasCaptureContext`: the surface opens the chat and attaches the PNG to its draft (`ComposerInsertion.files`).

## Chat, models, and tools

| Boundary | Contract |
| --- | --- |
| Chat stream | `/api/chat` SSE carries tokens, usage/tool events, completion, and failures. Keep proxy buffering disabled for streaming. |
| Project context | Bind memory scope to the chat's containing project/tab, not the project selected elsewhere. Support branch/merge histories: branch, merge, move and (cascade) delete commit all their chat and `project.json` writes and deletes in one unguarded `DataStore.apply` transaction, upload cleanup runs after it. |
| Providers | Every backend model call (chat, tools, OCR, memory extraction, web-search planning, sandbox plots) goes through `lib/completions.py`: the plain `openai` SDK on pi-host's completion gateway (`pi_host.gateway_url()`, bearer `pi_host.token()`), model `pi_models.gateway_model_id(selector)`. Stored selectors keep their spelling and are translated only at this call (`litellm_proxy/x` -> `x`, `gemini/m` -> `google/m`, others unchanged), so the gateway serves exactly the providers Pi has logins or keys for, Ollama included (see Pi model source). A model it does not serve fails with `ModelNotServed` naming the selector, sent to the browser like any provider error. The gateway clamps `reasoning_effort` per model and ignores `response_format` (memory extraction parses JSON from the text). Use stored model defaults, not hard-coded production models. |
| Search | Brave LLM Context retrieves passages with backend-only `BRAVE_API_KEY`, then the selected model generates cited answers. |
| Research | GPT-Researcher uses its DuckDuckGo retriever (package `ddgs`) for multi-step research. ### Collapsed chat rendering

- `features/chat/ChatPair.tsx` defers collapsed Markdown and equation rendering until near the viewport or focused. Hidden tabs stay deferred until shown, while headers, tool labels, and screen-reader text remain available.
- Expanding a turn renders its full content and plots.

### Sandbox checkpoint boundary

- Keep workspace-agent and plot slots scoped by user, chat, and sandbox scope. `SandboxRuntimeState` survives request-scoped service facades within one backend process and serializes each slot, not all chats. Uncheckpointed state is not shared across worker processes or recovered after process loss. Checkpoints and `delete_chat_state` run their store IO in a worker thread while holding the slot lock and `SandboxRuntimeState.assets_lock`, so asset garbage collection never sees a half-written checkpoint. Its asset deletes stay on the event loop, atomic with runs staging outputs there.
- Persist rich output assets immediately, but stage the latest workspace archive/manifest in memory. `routes/histories.py` checkpoints that workspace only after saving the corresponding chat successfully. Do not treat a finished tool call as a durable workspace checkpoint. `SandboxStore.checkpoint` writes the slot, manifest, active pointer and every run record in one `DataStore.apply` transaction; `recover_completed_run` only heals records written before that.
- Reuse completed `tool_call_id` results. Refuse a still-running record as busy, allow abandoned records older than five minutes to run again, and release native run/restore resources even on cancellation.
- Resume only a manifest with a Pi session (`pi_sessions`). A stored schema-1 manifest (`omp_sessions`, before Pi) decodes in `SandboxStore` without its session: the next run restores its workspace and starts a fresh Pi session, and its OMP session asset is no longer referenced.

### Live attachments and extraction

- Store source references in `Attachment.vaultPath`. Re-read active references on send/chat open and refresh previews before editor writes. Deduplicate reads per source, defer inactive references.
- Relocate moved files only when the original mount contains exactly one matching filename. Missing/ambiguous references keep read-only last text.
- Skip repeated missing-file reads on send, retry on preview opening, and preserve state for other read failures.
- Save text/task-list edits through the original write path before updating chat state. Never text-save PDF/image attachments.
- Sync changed referenced PDF bytes into the shared library and invalidate cached extraction. Deduplicate queued/extracting content and discard superseded results.
- Keep previous extracted text while replacement runs. The first send after a file change may use old text. Continue resolving legacy `PDFs/<name>` references.
- Run one extraction worker per backend process to avoid competing parses within that process. The queue/pending set is process-local, not a cross-worker lock. `mineru.parse_pdf` always runs MinerU into a temp directory: the per-user `Mineru/<stem>.md` asset is the only extraction cache, nothing on disk is reused. Persist results to PostgreSQL and mirror PDF/Markdown/images as convenience copies. Mirror failures do not invalidate authoritative database writes.
- Key the per-user PDF library by filename (`PDFs/<name>`) and extraction by filename stem (`Mineru/<stem>.md`, `Mineru/images/<stem>/`). Reusing a filename replaces that library entry, not a second independent document.
- List a finished extraction in the project's files: `POST /api/documents/write-binary` (project upload) and `POST /api/fileroots/add-to-project` (mounted PDF) queue the PDF with an `on_markdown` hook (`materialize`, `sync_pdf`), which calls `document_service.add_extraction` once the Markdown is cached (at once on a cache hit). It stores `project/<slug>/document/<stem>.md` and adds it to `project.json`, keeping an existing document of that name, so an edited copy survives a re-extraction. Images stay in the library, the Markdown keeps its relative `images/` links. The hook writes as no device (`deps.get_extraction_publisher`), so the sidebar of the uploading device reloads the project's files on the `chat/<slug>/project.json` change event too. The queue deduplicates by name and content: the same PDF queued twice at once lists its Markdown only for the first project.
- The sidebar shows no row for that Markdown: `workspaceTree.extractionsOf` pairs each project PDF with `<stem>.md` (stored, or where opening it moved it, `…/workbench/markdown/<slug>/<stem>/<stem>.md`), hides it and deletes it together with its PDF in one deferred delete. It is the PDF's Text view instead (see PDF viewer).
- Keep pasted images, drawings, canvas images, and architecture source attachments as snapshots. Reattach for later changes.
- Use `MINERU_SERVER_URL` for external OCR. Without it, the backend can spawn local MinerU per parse.

## Agent factory

A factory task is a pi-host `coding` session plus a row in `factory_tasks`. The Pi extension `~/.pi/agent/extensions/factory/` (source in `~/.os`) drives the pipeline inside that session and records every step as a `custom` entry, so the session file is the task's full record and its only state. The backend sets tasks up, relays commands and lists them, the frontend renders boards and task views from the entries.

```text
POST /api/factory/tasks -> workspace (worktree or current checkout) -> coding session -> /factory start <json>
  worktree task, run opens (start, retry, message) and merge: squash, rebase onto settings.branch (the target branch)
    conflict -> conflict round      other failure -> blocked (rebase_failed: <git error>)
  round 1..maxRounds: coder turn, then in agent_before_settle:
    hooks.after_code -> gates -> protected paths -> review     a problem: factory-feedback, next round
  empty diff                      -> done (no_changes)
  no passing round                -> blocked (max_rounds: <trigger>)
  merge auto                      -> merging -> done
  merge review                    -> waiting_approve -> /factory approve -> merging -> done
  a user message to waiting_approve, blocked, done -> new rounds on the same branch, merged again
```

| Owner | Contract |
| --- | --- |
| Extension | `~/.pi/agent/extensions/factory/index.ts` (a Pi user extension from `~/.os`, see `.docs/agent-factory.md`, "Where the plugin lives"), loaded into every unrestricted session, inert without a `factory-task` entry. Command `factory`: `start <json>` (`{ request, title, settings: { branch, merge, maxRounds, review, models: { coder?, reviewer? } } }`, `branch` the target branch, `sourceBranch` the branch the backend made the worktree off, both already resolved), `approve`, `retry`, `cancel`, each answers the RPC prompt with `disposition: "handled"`. Commands run in their own process group, killed as a group. While a round, review or merge runs, status key `factory` is set (plus `session-liveness` during a merge, which runs outside an agent run), keeping the session from idle eviction. |
| Configuration | `factory.yaml` and the role prompts `.factory/agents/coder.md` (system prompt section `factory_role`) and `reviewer.md` (the reviewer's appended system prompt) are read with `git show <commit>:<path>`, never from the tree the coder edits: a worktree task reads them from `git merge-base HEAD refs/heads/<mainBranch>` when a run starts, a current-checkout task from `baseSha`. | Diff base | Worktree task: `git merge-base HEAD refs/heads/<mainBranch>` (`taskBase`). A conflicting rebase is aborted and opens a `conflict` round whose `factory-feedback` lists the files and has the coder rebase and resolve; a rebase the coder left open gets that feedback again and is never aborted. A `conflict` round counts against `maxRounds` (`max_rounds: conflict`); at rest it opens the run in place of the `retry` or `message` round. Any other failure (a deleted branch, an untracked file in the way, an autostash that does not apply) opens no run and ends `blocked`, reason `rebase_failed: <git error>`; retry or a message tries again. The factory's commits run with `--no-verify --no-gpg-sign`, rebases with `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR=true`. |
| Merge | Worktree task: rebase as above (a conflict opens a `conflict` round at once), then the repository's merge queue (`queue.ts`: one ticket file per merge in `<git common dir>/factory-merge-queue`, first come first served, a ticket whose Pi process ended is dropped; status `queued for merge, N ahead`). While queued, every merge that lands on the target rebases the waiting ones, a conflict leaves the queue for a `conflict` round. On its turn: rebase, `merge_gates` (`factory.yaml`, the tests; `gates` when unset, then skipped when the rebase left the merge base where it was; a failed merge gate opens a `gates` round on the rebased branch, exit 75 ends `blocked`, `infra: …`), then in one `flock` holder on `<primary>/.git/factory-merge.lock`: a target checked out in a worktree (`git worktree list`, the primary or another one) is fast-forwarded there (`git merge --ff-only`, refused by that checkout's own uncommitted changes as `merge_failed`); a target checked out nowhere is moved with a compare-and-swap `git update-ref` against the commit the merge read. A target that is no longer an ancestor of the task's commit (another merge landed during the merge gates) moves nothing: the merge rebases again, runs the merge gates again and retries, `MERGE_ATTEMPTS` (3) times in all. When a fast-forward in the primary changed `uv.lock`, `package-lock.json`, `bun.lock` or `bun.lockb`, `hooks.after_merge` runs there (a failed hook leaves the task `done`, reason `merged, after_merge failed`); a ref update runs no hooks. Current-checkout task: commit only the paths that differ from the baseline, minus protected ones, built in a scratch index so the user's staged files stay staged; `review` leaves the change uncommitted until approve. Before any commit the checkout must be on the task branch with no merge, rebase, cherry-pick or revert in progress. A failure writes `factory-merge {ok: false, error}` and ends `blocked`, reason `merge_failed`. A diff that touches a `protected` glob is a round problem, never merged. |
| Abort and cancel | A plain abort (Esc, RPC `abort`) ends `blocked`, reason `stopped`, and never merges: the auto merge runs in `agent_settled`, where the abort is visible. Gates or a review already running finish first, their result is discarded. `/factory cancel` kills the running command group at once and ends `cancelled`, also from an idle `waiting_approve` or `blocked`; cleanup (`git rebase --abort`, index restore) still runs. The backend always cancels through the prompt. `/factory retry` works from `blocked` and `cancelled`; `retry` and `message` rounds (and a `conflict` round opened in their place) get a fresh `maxRounds` budget, round numbers keep counting. A message queued while the pipeline runs opens a `message` round. `/factory approve` answers at once and merges in the background, its completion is the `factory-state` entry. |

| Backend | `src/lib/factory.py` (models, `FactoryStore`, settings chain, diff, task life) and `routes/factory.py` under `/api/factory`, host-gated. `repo` is the primary checkout's absolute path everywhere. `GET/POST /repos` (`POST` refuses a path that is not the top of a primary checkout), `GET/PUT /settings?repo=`, `GET /branches?repo=` (the repo's local branches, alphabetically, case-insensitive), `GET /tasks?repo=` and `GET /tasks/{id}` (row plus `factory` `{state, round, reason, at}` and `live` from pi-host's session list), `POST /tasks` (`resolve_branches`, workspace, session, `/factory start`, row; no `factory-task` entry within 4 s cleans everything up, 502), `GET /tasks/{id}/diff` (`{base, diff}`, untracked files included, read-only), `POST /tasks/{id}/{approve,retry,cancel}` and `/messages` (open the session `ResumeById`, then `prompt_session`, a message as `followUp`), `POST /tasks/{id}/session` (open only), `DELETE /tasks/{id}` (409 while `running` or `merging`; stops the preview, a `PreviewError` is 502 and removes nothing; then session file, reviewer sessions, workspace, row). A current-checkout start, retry or message holds `pg_try_advisory_xact_lock` per checkout across the busy check and answers 409 when it is taken or another task of the checkout is `running`, `merging`, `waiting_approve` or just started. The timeline reads `GET /api/pi/sessions/{id}/entries?customType=factory-&since=<entry id>`. |

## Neovim sessions

- Consume `neovim_available` from `/api/config`, not a frontend reconstruction: require host access, `nvim` on backend `PATH`, and `$XDG_CONFIG_HOME/nvim` (default `~/.config/nvim`) directory. Settings opt-in is per device.
- Run one `nvim -n` PTY per session through `WS /api/neovim/session`, rendered by xterm.js. The session opens one document, `{"type":"open_file","path"}` adds more. Each document is a private temporary copy in a directory of its own (equal basenames never collide) and its own buffer, kept loaded and hidden while another shows. Switching never saves. Start in the innermost containing mount or home for database documents.
- Route `:w` through RPC to the browser's normal document API, including architecture validation: each buffer has its own `BufWriteCmd` and the browser gets `{"type":"save","id","path","content"}` for the buffer written. Replace the buffer with stored text if rewritten. Leave modified on failure. The temporary copy is not canonical storage.
- The session keeps `base` per document, the text Neovim and storage last agreed on. Browser `{"type":"set_content","content","path"}` (agent or remote edit on disk) addresses one buffer, hidden ones too, and is ignored when `path` is not open. It replaces an unmodified buffer and merges into a modified one with `text_merge.merge_theirs` (`git merge-file -p --theirs`: the incoming side wins conflicting or adjacent lines), keeping it modified. This is deliberate: show no conflict notice or markers, and leave saving in time to the user. Only changed line ranges are rewritten (`gigachad_set_text`, `vim.diff` hunks), so the cursor stays on its text.
- `:w` of an absolute disk file whose disk text differs from `base` saves the merge of buffer and disk instead, echoing "Saved, merged with the agent's edits". Unreadable or non-UTF-8 disk text or a refused merge fails the save and keeps the buffer modified. `set_text` waits for a running `:w` of its document, `set_content` frames run as ordered tasks so a save's reply is never blocked.
- Keymaps that notify the browser are one list (`neovim_session._KEYMAPS`, `{mode, lhs, event, suffix?}`), passed to Lua for the events the session has a callback for and installed per tracked buffer by one loop (`install_keymaps`). A `suffix` keymap applies only to buffers whose path ends in it, re-checked on rename. Visual `<leader>a` (`selection`, with `ask_keymap` on open) reports `{"type":"selection","path", start_line, end_line, text}` (full lines of the buffer at `path`), normal `<leader>v` in `.tex` buffers reports `forward_search`.
- Incoming control frames are pydantic models (`_Control` subclasses in `routes/neovim.py`) dispatched through one `handlers` dict in `_relay_input`. A malformed frame is ignored. Session work that fails is logged (`_guarded`), not raised. Outgoing events go through `_BrowserSaves.notify` (ordered notice queue). Frontend: `useNeovimTerminal` (`features/editor/NeovimEditor.tsx`) returns `send(NeovimCommand)` (false without a session) and takes `on` handlers per `NeovimEvent` type. Commands and events are typed in `features/editor/neovimProtocol.ts`. `QUEUES_WHILE_CONNECTING` says per command whether it waits for the open frame while the socket connects (`open_file`, `renamed`). `set_content` keeps the latest text per path until the open frame instead, the others are refused.
- Buffers: `open_file` loads the file at `path` from disk (`disk_file`, UTF-8) into a new private copy when it is not open yet and shows it, else it just shows the open buffer. A file that cannot be read answers `{"type":"open_failed","path","message"}`. `{"type":"switched","path"}` reports the tracked buffer Neovim shows whenever Neovim itself changes it (`:bnext`, `:b`), not after an `open_file`. `{"type":"insert_lines","text"}` inserts lines below the cursor of the shown buffer and puts the cursor on the first one.
- `{"type":"renamed","from","path"}` renames the buffer of `from` in place (`gigachad_rename`), keeping its text, cursor and modified flag, drops its old private copy and moves the path saves and merges use. It does nothing when `from` is not open and logs a refusal when `path` is open already. `useNeovimTerminal` sends it for `renameFile(from, to)` and by itself when `document.path` changes under the same `key`. The route resolves only the target the document's kind needs (`NeovimSession.is_notebook_text(from)`: `notebook_buffer`, the new virtual name, else `disk_file`, the file `:w` merges with), `NeovimSession.rename(from, path, target)` applies it. Path validation stays in the route, document kinds in the session.
- Notebook text (`open` with `"notebook": true`): the document is a notebook's whole percent text (see Jupyter notebooks, Neovim beside the notebook). `path` must be `<notebook>.ipynb<ext>` with `ext` matching `\.[A-Za-z0-9]{1,8}` and the notebook a readable file under the file roots (`notebook_buffer` in `routes/neovim.py`, `disk_file`), else the socket closes with 1003 like a malformed open. `nvim` starts on an empty placeholder in the session tmpdir (never without a file argument, so session-restore and dashboard plugins stay idle). The buffer takes the virtual name `<resolved notebook><ext>` beside the validated notebook (never the raw path), so the user's LSP finds the notebook's project and `.venv` and picks the filetype. Nothing is ever read from or written to that name: `BufReadCmd` loads the text last agreed on through the internal RPC request `base` (also for `:e!`, the first load is no undo step), a `FileReadCmd` matched on the escaped virtual name refuses `:r`/`:r %` (Neovim fires it without a buffer, so a buffer-local one never matches), `BufWriteCmd` sends `:w`, `:w!` and `:up` to the browser as `save`, `FileWriteCmd`/`FileAppendCmd` refuse partial writes and appends (`:1,2w`, `:w >>`) with "The notebook is only written whole, with :w", no swap or undo file, and no `disk_path`, so `:w` never merges disk text. `:sav`/`:file` get the virtual name back (`BufFilePost`, after the command) and a rename wipes the buffer left under the old name, so `:e #` reads nothing. With a stale file at the virtual name a plain `:w` is refused (E13), `:w!` still saves through the browser. The buffer keeps an empty `buftype` on purpose: with `acwrite` `vim.fs.root` ignores the buffer name and the LSP loses the project. `renamed` keeps the virtual naming for a valid new notebook text `path` and is refused (logged) without one.
- Each session document has one typed backing (`neovim_session.py`): `_PrivateCopy` (its own file in the session tmpdir, `disk_path` for the merge on `:w`) or `_NotebookText` (the virtual name). Only a private copy is renamed onto a sibling name and unlinked, a virtual name can never be deleted. The Lua setup receives one named options table (`channel`, `first_path`, `notebook`, ...).
- Notebook keymaps, buffer-local in normal and insert mode on the notebook text only: `<C-CR>` writes through the normal `:w` path and, only when that save was stored, notifies `run_cell` with the cursor line. The socket sends `{"type":"run_cell","path","line"}` (1-based line of the text just saved) through the ordered notice queue, after the save it follows resolved. A failed save runs nothing and echoes the error. `<S-CR>` does the same, then puts the cursor on the line after the next `# %%` marker (Lua `is_marker`, the rule of `^# %%(\s.*)?$`): a marker on the last line gets one empty line appended, without a next marker `""`, `"# %%"`, `""` are appended (the buffer becomes modified) and the cursor goes to the last line. Insert mode stays insert mode. xterm sends a plain Enter for Shift+Enter and Ctrl+Enter, so `NeovimEditor` sends them as CSI-u (`ESC[13;2u`, `ESC[13;5u`) for a `notebook` document only.
- Every session sets `more` off and `messagesopt=wait:2000,history:500` once the user's config ran, because a message longer than the command line (an LSP client quitting) would stop Neovim at a hit-enter prompt where it answers no RPC request. What the user's config prints before that is out of reach.
- Terminate/remove the copies on `:q`, document close, or disconnect. Unsaved edits are unrecoverable. Preserve the session across preview/fullscreen switches. Terminal focus owns all keys, including Escape.
- Esc in normal mode gives focus back to the app: a global normal-mode `<Esc>` mapping (installed after the user's config) runs the user's own `<Esc>` mapping (`:noh`) first, then notifies `leave`, the socket sends `{"type":"leave"}` and the browser focuses the closest focusable element around the terminal (`[tabindex]`), else blurs to the page. Buffer-local `<Esc>` mappings win over it, a plugin that maps `<Esc>` later replaces it.
- Yanks reach the browser clipboard: a `TextYankPost` autocmd notifies over RPC, the socket sends `{"type":"yank"}`, the browser writes it best effort.
- The browser is Neovim's clipboard, never the machine Neovim runs on (on the deployed server that is not the user's). After the user's config the session sets `vim.g.clipboard` to a gigachad provider for `+` and `*` (replacing the user's provider, `clipboard=unnamedplus` decides which registers reach it). A paste is `vim.rpcrequest(channel, "paste", <path of the buffer>)`, so the backend sends `{"type":"clipboard_read","id","path"}` and waits for `{"type":"clipboard","id","text"}` or `{"type":"clipboard","id","error"}`. A text ending in a newline pastes linewise below the cursor, else charwise, an empty text pastes nothing. An error answer, no answer within 15 s (a permission prompt can take time, Neovim shows "Clipboard did not answer") or a closed socket shows the message as an error and pastes the last yank of Neovim itself, since the provider's copy keeps its lines and regtype locally: `yy` then `p` never depends on the browser. The read is handled beside other requests, so a waiting paste holds up no `set_content`, `:w` or `insert_lines`. `{"type":"message","text"}` shows `text` as an error for failures without a request (an image of a paste event that could not be stored). `useNeovimTerminal` answers `clipboard_read` from `navigator.clipboard.read()`: `text/plain` pastes as text, a PNG without text is stored as an image (see Images in the Workbench), a denied permission answers `error: "Clipboard access denied"`. Chrome asks for the permission once, Firefox and Zen show a paste button on every read.
- Theme the terminal from the app. The browser sends `{"type":"background","light"}` on open and on every theme flip, and the backend sets Neovim's `'background'` over RPC once setup finished, so the user's colorscheme reloads its light or dark palette. The palettes themselves live in the user's Neovim config, not this repo.
- Treat as host code execution. Match WebSocket origins to `GIGACHAD_CORS_ORIGINS`, or loopback for development `*`.

## Shell terminal

- `t` outside a text field (composer, input, select, terminal, a canvas that took the key) opens the active tab's floating login shell (`ShellTerminals` in `features/editor/ShellTerminal.tsx`). Logins without host access get no shortcut.
- One shell per tab, by tab id: `AppShell` hands `ShellTerminals` the active tab id and the open tab ids (from `TabManager`'s `onActiveTabChange`/`onTabsChange`), so a tab's own content remounting (a new chat in it) keeps its shell. Only the active tab's window shows, other tabs' shells keep running hidden. Closing a tab unmounts its shell, which hangs it up.
- Each shell is one `WS /api/terminal/session` (`routes/terminal.py`): first frame `{"type":"open","rows","cols"}`, then binary keystrokes, `{"type":"resize"}` and `{"type":"escape"}`. Output is binary, `{"type":"leave"}` answers an Esc at the prompt, `{"type":"exit","code"}` follows the shell's end. It runs `$SHELL -l` (else the account's shell) in the home directory with the backend's environment (`pty_process.terminal_environment`). A backend restart (dev `--reload` too) ends every shell.
- Esc is the backend's call (`PtyProcess.is_in_foreground`: the shell's own process group holds the terminal): at the prompt it answers `leave` and the window hides, while a program runs (vim, less, fzf) the program gets it. A second Esc within 400 ms hides the window anyway. Esc never reaches the shell's line editor at the prompt (no vi mode). A click beside the window hides it too, the shell keeps running and `t` shows it again. `exit` ends the shell and closes the window. A dropped connection offers a restart.
- Disconnect hangs up the shell's process group (SIGHUP, an interactive shell ignores SIGTERM), SIGKILL after 2 s (`PtyProcess.close`). Gate and trust: same as Neovim, host code execution behind `is_allowed_websocket`.

## Jupyter notebooks

- Open `.ipynb` in `@datalayer/jupyter-react` (`features/notebook/`, a `document` tab item that `WorkspaceSurface` routes to `NotebookWorkbench`, loaded with `next/dynamic` and `ssr: false`, keyed by tab and the `useEditorPath` generation so a rename never remounts and another file in the tab gets a fresh editor). Requires host access like Neovim: every route has the host-access gate.
- **Tab shell** (`features/workbench/NotebookWorkbench.tsx`): the notebook tab has the workbench's top bar and chat drawer. `WorkspaceSurface` gives a notebook `document` item the same bar as a `workbench` item (`workbenchAgent` and `workbenchStatus` slots, plus a `center` slot for the notebook, theme, close, "Open chat" while the drawer is closed, one drawer state for both). `NotebookToolbar` (run, run all, interrupt, restart, add cell, kernel `PopoverSelector`) portals itself into `center` (`InTopBar`). The notebook has no toolbar row of its own. The chat is `WorkbenchChat`/`useWorkbenchChat`, shared with `Workbench`: a Pi `document` session in the tab's file panel, reasoning and model pickers in `workbenchAgent`. It is linked to the notebook's absolute path (`POST /api/workbench/chat`, no prepare: notebooks are always disk files) and runs in the mount root holding the notebook, else its folder, where its kernel runs too, so the relative links Pi opens resolve against the mount; its first message names the file (`fileLead`). Visual `<leader>a` in the Neovim pane quotes into the chat draft: the backend reports lines of the percent text, `NotebookWorkbench` puts the notebook's path on them (`analysis.ipynb:2-3`) and fences them in the language of the buffer's extension (`.ipynb.py` python, any other extension as is).
- **Endless view**: the notebook item runs under the top bar (`runsUnderTopBar`) like the markdown preview. `NotebookEditor` sets `--gc-nb-top` to `PANE_TOP_PX` (`WorkbenchSplit.tsx`, the preview page's top), `notebook-theme.css` pads the windowed panel's viewport by it and gives its scroll container (`.jp-WindowedPanel-outer`) the same `scroll-padding-top`, so a revealed cell never lands under the bar.
- **Restart revives a dead kernel**: the toolbar's restart restarts the session's kernel. When the kernel is `dead` or the restart fails (the Jupyter server restarts with the backend and forgets its kernels), it starts a new kernel of the same spec through `POST /api/jupyter/kernel` as a kernel switch does (the old session is shut down, the library connects to the new id).
- Adapter exception: `@jupyterlab/services` speaks the Jupyter protocol from the bundle, but through the backend proxy only (`createNotebookServiceManager` points it at `/api/jupyter/server/` with a dummy token). Jupyter imports stay in `features/notebook/` (eslint), server URLs, token and response shapes stay in `src/lib/jupyter.py` (`routes/jupyter.py` only maps errors, Pydantic models validate what it reads, 503 unavailable, 502 invalid shape).
- **Jupyter service** (`src/backend/jupyter_service.py`): one uvicorn process `run-backend.sh` starts before the workers, on the Unix socket `GIGACHAD_JUPYTER_SOCKET` (`~/.local/share/gigachad-bot/run/jupyter-<profile>.sock`, a 0700 folder only the user can enter, no reload). It alone holds `JupyterHost`: the server, its token and the kernel map, so every worker sees the same kernels (with one server per worker, a kernel started through one worker was unknown to the next request's worker). Workers keep the browser checks (host access, trusted request, file roots, proxy allowlist) and reach it through `lib/jupyter_service.py`'s `RemoteJupyterHost`, which has `JupyterHost`'s methods and errors (service down: 503). Kernels survive backend reloads and end with the service; the script stops everything when any of backend, C4 or Jupyter service exits.
- **Server supervision**: `JupyterHost` starts `python -m jupyter_server` from the app venv on a free loopback port at first use, restarts it after it died and stops it with the service (`jupyter.shutdown()` in its lifespan, `atexit` and a parent-death watcher in the bootstrap). Kernels get SIGKILL when the server ends in any way, see Host processes. Config files are ignored, runtime files live in a temporary folder, kernelspecs and `server.log` in a private `jupyter_home()`.
- **Token**: generated by the service and set in the server's memory by the bootstrap, never in its environment, argv or a file its kernels can read. The proxy drops the browser's `token`, `_xsrf`, cookies, `Authorization`, `Origin`, `Referer` and identity headers (`browser_request_headers`, in the worker and again in the service) and injects its own `Authorization`.
- **Proxy** `/api/jupyter/server/{path}` (HTTP streamed through the shared `reverse_proxy.streaming_response`, WebSocket for kernel channels):
  - Allowlist `is_proxied_path`: `api/kernels`, `api/kernelspecs`, `api/sessions`, `api/events` (with sub-paths), `api/status`, `api/me` and kernelspec resources. Everything else is 404 (no `api/contents`, no terminals)
  - Reads are `GET` and `HEAD`. Writes are only kernel `DELETE`, kernel `restart` and `interrupt`, and session `POST`, `PATCH` and `DELETE`. Anything else is 405
  - A session request must name the id of a kernel this host started (`check_session`), so the browser can bind a notebook to its kernel but cannot start one. Kernels start only through `POST /api/jupyter/kernel`
  - **Trusted-request gate**: every HTTP route depends on `require_trusted_request` (`websocket_origin.py`): a request that changes anything needs a trusted `Origin`, a read without `Origin` must not be cross-site per `Sec-Fetch-Site`. The WebSocket upgrade uses `is_allowed_websocket` (trusted origin plus host access)
- **Kernel per path**: `POST /api/jupyter/kernel {path, name}` returns `{kernel_id, name}`. The notebook path goes through `FileRoots` and is resolved once (`notebook_path`), that key is the kernel map and the venv search root. The kernel's working directory is the file mount holding the notebook (`FileRoots.root_of`, the same root Neovim's cwd uses), so repo-relative paths work from `<mount>/notebooks/x.ipynb`; a notebook outside every mount runs in its folder. The notebook's Pi chat runs in the same directory (`POST /api/workbench/chat`), so relative file links resolve against the mount root too. The same path and name reuse the running kernel, another name replaces it. `DELETE /api/jupyter/kernel?path=` ends it (204, idempotent).
- **Kernelspecs** `GET /api/jupyter/kernelspecs?path=` returns the default and the specs. Specs are the ones Jupyter discovers plus one generated spec per `.venv` in the notebook's folder or an ancestor up to `$HOME`, named `venv-<hash>` and shown as `<parent>/.venv`, written below `jupyter_home()` and never in the user's folders. The default is the notebook's `metadata.kernelspec.name` when listed, else the nearest venv, else the app's own `python3`. A venv without `ipykernel` (found by file, a listing never runs a venv's python) is flagged `needs_ipykernel`, the picker shows "(install ipykernel)" and the first start runs `uv pip install ipykernel` into it (180 s). The pick is stored as the notebook's `metadata.kernelspec` and saved with the file.
- **Rename and delete**: the documents routes call `jupyter_service.host().move_kernel(old, new)` after a rename or move of a file and `shutdown_kernels_under(path)` after a delete, so the kernel follows the file and ends with it. A service that does not answer has no kernels, so these log and go on.
- **Tab close**: `TabManager` announces `announceFileClosed(path)` (`lib/backend/fileEvents.ts`) when no tab holds a file any more, and `useKernelShutdown` (mounted once) sends `DELETE kernel` for `.ipynb` paths. Switching tabs or reloading the page does not shut down.
- **Reconnect by path and idle cull**: a remounted editor repeats `POST kernel` with the same path and name and reattaches to the running kernel. The server culls kernels nobody is connected to after 2 h idle (`cull_idle_timeout`, checked every 60 s), so a closed browser frees them.
- **File sync**: the file API owns load and save, the library only edits the shared model.
  - `useNotebookFile(path)` is `useRootFileDocument` with a notebook codec plus `useDebouncedCall` (800 ms of quiet after a model change, `save()` for Ctrl+S and the notebook text store, resolving false when the write failed, pending changes saved when the model goes away). It returns `initial` for the first render only, later changes never go through a prop
  - `serializeNotebook` keeps the file's style (1-space indent, key order, trailing newline, `orig_nbformat`), strips library-injected `metadata.editable` unless the source had it, and a save whose normalized content equals the disk never writes. This also ignores the write's own echo from the file watch
  - Follow: `useFollowFiles` feeds a disk change to `applyIncomingNotebook(model, base, incoming)` which applies `diffNotebook` ops to the shared model, so only changed text moves the cursor
  - **Cell diff policy** ("merge theirs") per field or metadata key: only the editor changed it, keep it. The file changed it, or both did, the file wins. Cells match by id (by position when any ids are missing or repeated). A cell the file deleted is deleted, a cell only the editor added is kept, the file's order wins when it moved a cell. A cell whose type or attachments changed is replaced whole
- **Neovim beside the notebook** (per device setting like every Neovim use): `NotebookWorkbench` lays the tab out through `WorkbenchFrame` like the Markdown workbench (see Workbench, Layout), Neovim left on an `EDITOR_PAGE`, the notebook right with its outputs, kernel, toolbar and editable CodeMirror cells. Both panes stay mounted and the hidden one gets `hidden`, so Neovim keeps its session and the notebook its kernel. With Neovim disabled (`editor: null`) the notebook is shown alone, without switch or session. The Jupyter model (Yjs, in the browser) is the single source of truth, the Neovim buffer holds a projection of it as one ordinary document.
- **Percent text** (`features/notebook/notebookText.ts`, `notebookToText`/`parseNotebookText`): every cell starts with a marker line (`# %%`, `# %% [markdown]`, `# %% [raw]`), cells are joined by one blank line, the text ends with `\n`, an empty notebook is `""`, outputs are left out. A code cell's body is its source, a markdown or raw cell's body has each line prefixed `# ` (an empty line `#`). Parsing: marker `^# %%(\s.*)?$` (Lua `is_marker` in `neovim_rpc.py` agrees), kind from the rest of the line (`[markdown]` or `[md]`, `[raw]`, anything else is a code cell's ignored title), trailing blank body lines dropped, `# ` or `#` stripped from markdown and raw lines, non-blank text before the first marker becomes a leading code cell. A code line that matches the marker splits its cell (as in jupytext), and trailing blank lines of a code cell are lost on a round trip. `cellAtLine(text, line)` gives the cell holding a 1-based line (0 before the first marker, null without cells).
- **Text to model** (`applyNotebookText`): the parsed cells are matched to the model's in three passes, LCS on exact type and source, then LCS per gap on the same type with line similarity ≥ 0.5 (`2·common lines / all lines`), then same-type cells by position in sub-gaps of equal size. A matched cell keeps id, metadata, outputs and execution count and takes the new source, an unmatched model cell is deleted, an unmatched text cell is inserted (`crypto.randomUUID()` id, empty metadata, code cells `outputs: []`, `execution_count: null`), in the text's order. Model cells are matched by synthetic keys `cell-<index>` (`toJSON` drops ids below nbformat 4.5), the result goes through `applyNotebookOps(model, diffNotebook(...))` of `notebookSync.ts`.
- **Text store** (`NotebookTextStore` in `notebookTextStore.ts`, `createNotebookTextStore`): `NotebookWorkbench` owns one store per Neovim session key and passes it through `NotebookDocument` to `NotebookEditor`, which binds its shared model while it holds one (`bind(model, persist, run)`, rebound on a new model or store, unbound on loss and unmount). `state()` is null while unbound, else `{extension, text}`: `extension` is `metadata.language_info.file_extension` when it matches `^\.[A-Za-z0-9]{1,8}$`, else `.py`, fixed while bound. `text` is the text last handed to Neovim and the stale-save baseline, moved only at bind, by a handout to followers and by `save`. Reading the store never moves it.
  - The text is `modelText(model)`: built from the cells' type and source only, never `toJSON()` with its outputs
  - `follow(push)` hands every change of the text to `push`, 150 ms after the last ydoc `update` (`NOTEBOOK_TEXT_DELAY_MS`), and catches up at once when the text moved since the last handout. The model's `update` is watched only while bound and followed. Followers survive unbind and rebind (StrictMode)
  - `save(text)` rejects with "The notebook is not loaded" while unbound. When the model moved since the last handout it hands the current text out and rejects with "The notebook changed, write again", so a `:w` never reverts a change Neovim has not shown yet. Else it applies the text (`applyNotebookText`), persists at once (`useNotebookFile().save()`, "Saving the notebook failed" when the write failed, the notebook shows the cause in its save error) and resolves the stored text
  - `runAt(line)` finds the cell with `cellAtLine` on the text the last `save` resolved with and runs it (`runCellOf`: active cell, `deselectAll`, `scrollToItem`, `NotebookCommandIds.run`, the focus stays in Neovim). Without a saved text it does nothing
- **Session**: `useNeovimTerminal` with `notebook: true`, path `<notebook path><extension>` (`analysis.ipynb.py`), keyed `<tab>:<generation>` from `useEditorPath`, the generation that keys the `NotebookEditor`: another notebook opened in the tab gets a fresh session and store, a rename keeps both and sends `renamed`. The session opens on `state().text` once the store is bound. While bound the workbench follows the store, Neovim open or not, so a session always opens on the current text, and `setContent(text, virtualPath)` drops a text while no session is open. Every model change (notebook UI, agent or disk edit through `applyIncomingNotebook`) reaches an open buffer that way: an unmodified buffer is replaced, a modified one gets it merged and stays modified (see Neovim sessions). `:w` goes to `textStore.save`, whose resolved text replaces the buffer text when it differs, a rejected save leaves the buffer modified. `run_cell` calls `textStore.runAt(line)`.
- **`:q`** (exit 0): the Neovim pane shows `NeovimStopped` with a "Start Neovim" button and the notebook stays. The button opens a new session on the store's current text. Another notebook opened in the tab is a new key and opens Neovim again. Any other end of Neovim shows `NeovimEditor`'s stopped state (`NeovimStopped` with the message and "Restart Neovim").
- **Notebook page**: the rendered notebook sits on `NOTEBOOK_PAGE` (`features/workbench/pages.ts`) inside `PanePage`, the primitive that places Neovim's page too, so both sides share top, width and height and the cells scroll inside the page, never under the top bar. Its toolbar and the view switch are raised pills (`TopBarPill raised`, `WorkbenchFrame raised`), the chat's model and thinking pills stay flat. Markdown cells render plain on that page.
- **Cell highlighting and the fork**: `features/notebook/syntaxHighlight.ts` passes one factory (`gigachad-syntax-highlight`, in a module-level array because the library rebuilds its features when the array identity changes, and factory names must be unique) through the `Notebook` `editorExtensions` prop. It is `Prec.high(syntaxHighlighting(HighlightStyle))` for calls (`t.function(variableName/propertyName)`), class names, `t.bool`, `t.escape`, `t.null` plus a small `ViewPlugin` that marks `self`/`cls` and decorator names with `gc-syn-*` classes, because Lezer's Python grammar has no tag for them. Upstream `@datalayer/jupyter-react` has no such prop, so `package.json` uses the fork's release tarball (upstream PR https://github.com/datalayer/jupyter-ui/pull/515). Back to npm once the PR is released: set the npm version, drop the URL, refresh the lockfile.

- **Shared proxy plumbing**: `src/backend/reverse_proxy.py` holds `streaming_response` (hop-by-hop headers dropped through `lib.upstream.forwardable_headers`) and `forward`, used by the LearnHarness gate and the Jupyter route. Errors reuse `lib/upstream.py` (`Upstream*`, `call_upstream`).

## Workbench (Markdown and LaTeX)

```text
open .md/.tex -> POST /api/workbench/prepare -> {path on disk, cwd = WORKBENCH/<kind> (mounted LaTeX: its project folder), kind}
  -> Workbench (WorkbenchFrame): Neovim (useWorkbenchEditor) | renderPane | Pi drawer (WorkbenchChat, cwd)
LaTeX: GET /api/latex/project?path= -> {folder, root, candidates} -> build root, chat keyed by folder
any writer (Pi, another agent, a shell, another device): WS /api/files/watch -> changed path -> onFileChange -> useFollowBuffers reads it -> setContent(text, path) -> Neovim merge
other device: POST /api/fileroots/file -> change event (key = absolute path) -> same onFileChange listeners
project folder: the same watch on the folder -> LaTeX build
```

- **Routing.** `.md` project files and mounted files, and `.tex .bib .sty .cls` files (kind `latex`, `workbenchKindOf`), open as `workbench` tab items when Neovim is enabled and the login has host access (`opensInWorkbench`), else in `TextDocumentEditor`. Notes (`note/...`) never do, `prepare` answers 400. A LaTeX file that lies inside the `texFolder` of an open workbench tab does not open a tab: that tab shows it as another buffer (`texProjectTab`, `texBufferShown`), see Buffers.
- **Images.** An image file (`kindOf` "image") from any source, a mount, a project file or a LaTeX project folder, opens as a `document` tab item. `DocumentEditor` routes it to `RawFileView`, which loads `GET /api/fileviewer/raw` (stored keys and host paths alike), so the text editor and its "not a text file" message never see it. Opened from a tab showing a LaTeX workbench it takes a new tab (`opensBesideWorkbench` in `TabManager.showItem`), so the Neovim session and unsaved buffers stay.
- **Prepare** (`routes/workbench.py`). A stored project document moves to `WORKBENCH/<kind>/<slug>/<stem>/<name>` through `document_service.move_to_folder` (references rewritten, row deleted, 409 on a name conflict), only after `roots.contains` confirms the target is readable later (else 403, nothing moved). An absolute path is checked with `resolve_allowed` and returned resolved. Prepare is not idempotent for keys: the frontend dedupes it per path (`usePreparedWorkbench`, StrictMode-safe) and replaces the tab item's path with the returned one. `POST /create` writes a new `.tex` (`latex.NEW_DOCUMENT`) or empty `.md` there and lists it; a folder that exists already answers 409 even without a file of that name (a leftover is never adopted). Deleting such a listed document removes its whole folder (see Delete cleanup).
- **Prompts.** `templates/workbench/{latex,markdown,pdf,canvas,notebook}.md`, rendered by `lib/workbench/prompts.py` (`{{TEMPLATES}}` becomes the absolute template-set folder, so the agent reads the sets where they ship), are the source of truth, appended to Pi's system prompt on every create and resume. The chat runs the user's full Pi (tools, extensions, skills, web, the cwd's `AGENTS.md` files), pi-host restricts it only when a request passes a tool allowlist. Each prompt carries the honesty rules it needs itself. The first plain message of a new session carries a lead: Markdown `File: <path>`, LaTeX `Project: <folder>, root: <file>` (just `Project: <folder>` without a root), canvas `Canvas: <name>`. The folder and a Markdown path are relative to the cwd when inside it, else absolute, the root is relative to the folder. The LaTeX prompt says the root builds, every other `.tex` starts with `% !TEX root = <relative path to the root>` (new ones too), images go in `imgs/` (fetched from the web when the user provides none) and are referenced relative to the project folder, never `\graphicspath`, and the PDF rebuilds on any file change so the agent never compiles. A presentation root sends the agent to its template set's `STYLE.md` and `example.tex` (see Presentations).
- **Pi chats.** `POST /api/workbench/chat {path, session_id?, new?}` opens a Pi `document` session (`lib.pi_host.open_session`, `profile="document"`) for an absolute file, LaTeX project folder, notebook or canvas key, with the rendered prompt sent on every create and resume; cwd: the kind directory (created when missing, nothing else creates it) for Markdown, PDF and canvas, the project folder for LaTeX (also at a mount or repository top), the mount root (else folder) for a notebook. An active session pi-host lost (404) is unlinked and replaced. `GET /chats?path=` lists the link with the linked `SessionInfo`s, `POST /chat/informed` clears `moved`. A PDF chat answers `pdf_text`: `{state:"ready", path}` (MinerU markdown mirrored to `Documents/Mineru/<stem>.md`) or `{state:"pending"}` with the extraction queued. `/api/pi/files?cwd=` serves `@` completion for a cwd inside the file roots or `WORKBENCH`.
- **Links.** `workbench/chats.json` keeps every Pi session of a chat key and its active one (`lib/workbench/links.py`, `SessionLinks`): a session id becomes active and is listed once, a new session is listed once linked, a bare id stored earlier reads as one session. The key is the absolute path of a Markdown file or notebook, the absolute project folder for LaTeX (every file of a project shares one chat), or a canvas key. Opening a folder without a link adopts the links stored under LaTeX files inside it (any depth): their sessions merge in stored order, the active one is the root file's (`latex.project_of`) else the first file's, `moved` merges, the file keys go and the store is written once. A relocation that changes a key's path (file or project rename) marks all its sessions `moved` (`workbench.links.owe_new_paths`, applied by the relocator to `chats.json`): the next message of each starts with the lead again, then `POST /api/workbench/chat/informed` clears it, so a continued session works on the new path. Every change is one read-modify-write under a process-wide lock, retried up to 10 times on a stale revision from another worker; `POST /chat` also holds a per-key lock, so two opens of one file in one worker share one session. Two first opens of one file on different workers can still start two sessions (both kept, the later one active). The omp-era `workbench/sessions.json` is no longer read or written.
- **LaTeX projects.** A project is a folder with a root `.tex`, a file with `\documentclass` before `\begin{document}` (comments ignored). `latex.project_of(path, ceiling=roots.ceiling_of(path))` resolves the root of any file and never reads above the ceiling (see `ceiling_of` under Primitives):
  1. A `.tex` whose first 5 lines hold `% !TEX root = <path>` (case-insensitive) takes that file, resolved against its own folder. The target must exist, be a `.tex` and lie inside the ceiling, else the comment is ignored.
  2. A `.tex` root document is its own root.
  3. `main.tex` of its folder.
  4. The only root document of its folder.
  5. Otherwise no root. The candidates are the root documents of its folder and of the 2 folders above, never above the ceiling.

  Other files (`.bib`, `.sty`, `.cls`, images) skip 1 and 2, take rules 3 and 4 from the nearest of those folders that has a root, and have no candidates. The project folder is the root's folder, else the file's. Routes (`routes/latex.py`, host access, 403 outside the roots):
  - `GET /api/latex/project?path=` answers `{folder, root, candidates}`.
  - `POST /api/latex/root {path, root}` writes `% !TEX root = <relative path>` as the first line of the `.tex` `path` (replacing its old one), records the change and answers the project. 400 unless both are `.tex` files and `root` is a root document inside `path`'s ceiling. The frontend asks for the project of every shown file (`useTexProject`, the last project stays while it loads). Without a root the PDF pane lists the candidates (`LatexRootPicker`, choosing calls `/root` then builds), or says "No root document" when there are none.
  - `POST /api/latex/file {folder, name}` creates a `.tex .bib .sty .cls` file through `DiskFiles` (one segment without a leading dot, else 400, 409 when it exists). A `.tex` starts with `% !TEX root = <relative path>` and a blank line when the folder has a root by rules 3 and 4, else with `NEW_DOCUMENT`. The others are empty. The sidebar offers it on a Code folder that directly holds a `.tex` and on a promoted folder, a name without extension gets `.tex`.
  - Build output (`latex.is_build_output`: inside `.latex-build/`, `*.view.pdf`, and the aux files `.aux .log .synctex.gz .fls .fdb_latexmk .out .toc .bbl .blg .bcf .run.xml` of a sibling `<stem>.tex`) is hidden from every tree, file list and the folder stamp (`file_walk`).
- **Promote.** `POST /api/workbench/promote {slug, path}` turns a listed `.tex` directly inside a workbench document folder `WORKBENCH/latex/<slug>/<folder>/` (any name) into its folder: `ProjectStore.replace_file` swaps the entry in place, a display name `X.tex` becomes `X`. 404 when the project does not list the file, 400 for any other shape, 409 when the folder is listed already. There is no way back. `GET /api/documents` lists such an absolute directory as `{mime: "inode/directory", children: <build_tree>}` under its display name, and the sidebar shows it like a mounted folder (files open, rename works). The hover action "Make LaTeX project" sits on those `.tex` rows. Deleting the entry deletes the whole workbench folder from disk (irreversible, undo only before the deferred delete fires); a mounted folder is only unlinked. A project rename moves the folder with the rest (`move_project_directories`).
- **Rename** (`document_service.rename_on_disk`, see Project file names). The disk file moves inside its folder and `chats.json` is rewritten where a key's path changed (the agent's own context still names the old path). `useFileRename` calls `announceFileMove({from, to})` (`lib/backend/fileEvents.ts`) and other devices reach the same `onFileMove` listeners through the `moved_to` change event. The shell moves the tabs, the sidebar reloads the Code tree and `useWorkbenchEditor` calls `renameFile(from, to)`, so `NeovimSession.rename` renames the buffer in place with its unsaved text and modified flag. The tab item takes the new path and keeps the path it was opened with as `WorkspaceItem.sessionKey`: the workbench stays mounted under that key, `usePreparedWorkbench` stays prepared and `Workbench` keeps its Neovim session key. `useLatexBuild` starts clean for a new root.
- **Buffers.** One tab shows every file of a LaTeX project. `WorkbenchItemBody` keeps the project folder on the tab item (`WorkspaceItem.texFolder`, from `loadTexProject`), and a path change under the same `sessionKey` is a buffer switch, not a remount. `useWorkbenchEditor` starts the session with the first path and loads each later file from disk once, then sends `open_file` through `send` (retried every 200 ms until the session exists). It keeps a `synced` map of every open file to the text Neovim and the disk last agreed on, and saves each `:w` to the path the `save` frame names, one write at a time. A `switched` event (`:bnext`) moves the item path to the shown buffer. A file that fails to load or open goes back to the previous buffer with a notice. A restart keeps only the first and the shown file. Without Neovim there is no buffer, the disk text is what the pane shows.
- **Follow buffers** (`useFollowBuffers`). Every open file is followed through `useFollowFiles` (see Follow primitive). A change of one reads the file and pushes it into Neovim with `setContent(text, path)` when it differs from its synced text, the backend merges it into unsaved edits. A push made while the Neovim session is still opening waits for its open frame (`useNeovimTerminal`), so none is lost. A `document` change event for any open path (other devices, the backend, this device's announced changes) reaches the same listeners.
- **Folder rebuild.** Files the user has not opened (the agent's edits, `.bib` files, images, shell edits) change the PDF too. `useLatexBuild` follows the project folder through `useFollowFiles([], build, [folder])` while a root exists, any changed file in it (not build output, `.git`, `node_modules` or editor scratch files) queues a build.
- **Inverse search.** A double-click in the PDF pane (`PdfViewer` `onPageDoubleClick`, page plus top-left PDF points at scale 1 and a `PdfWord`, text geometry in `components/content/pdf/pdfText.ts`) goes through the inverse search hook of `features/latex/useSynctex.ts` to `POST /api/latex/synctex {path: root, page, x, y, word?, offset?, occurrence?}`: `synctex.synctex_source` (`lib/synctex.py`) runs `synctex edit` against `.latex-build/<stem>.pdf` (the `.synctex.gz` of the last build attempt, 10 s timeout) and answers `{path, line, column}`. Beamer reads a frame body as an argument, so SyncTeX reports its `\end{frame}` line: `word` (the double-click's native word selection, else the page's word nearest the spot) refines it to the first line from the enclosing `\begin{frame}` that contains the word (`synctex.refine_line`, frame bounds from `lib/tex_source.py`, a whole word that is not a `\command` name first, exact case, then any case, comments ignored), else the SyncTeX line stays. `offset` is the clicked character in the word (measured on the text layer's glyph boxes, else taking glyphs as equally wide) and `occurrence` which of the equal whole words of its rendered line (the text items on its baseline) it is: `synctex.word_column` picks that occurrence among the source line's whole words (clamped, `\word` command names and comments skipped, the word NFKC-normalised) and answers the 0-based UTF-8 byte column of that character, 0 without a word or a match. Errors: 404 without a match, 403 for a source outside the roots (theme and class files, the pane treats it like 404), 503 without `synctex`. `WorkbenchPane.editor.reveal(path, line, column, {focus: true})` sends `{type: "open_file", path, line, column?}` (cursor to the clamped line and byte column, centred, `_G.gigachad_goto_line`) or switches buffers first and keeps the line and column across the open retries. The editor pane comes back if the view hid it, then the terminal takes focus. Only the latest lookup acts (`hooks/useLatestRequest.ts`), an overtaken answer is dropped.
- **Forward search.** Normal-mode `<leader>v` in a `.tex` buffer (installed when the session has `on_forward_search`) sends `{type: "forward_search", path, line}` to the browser. The forward search hook of `useSynctex.ts` calls `POST /api/latex/synctex/view {path: root, file, line}`: `synctex.synctex_view` runs `synctex view` and answers `{page, x, y, words}`. Inside a beamer frame it asks for the frame's `\end{frame}` line (SyncTeX attributes the whole body there), `words` are the cursor line's printable words (`synctex.line_words`: comments, math, options and non-printing arguments stripped). `PdfViewer` `reveal {page, y, words, key}` scrolls the first page text item matching a word (else `y`, else the page top) into view and marks it. The PDF pane comes back if the view hid it. 404/403 show "No PDF spot for this line".
- **Download and present.** The LaTeX top bar shows `DownloadPdfButton` (fetches the built PDF as a blob, saves `<root stem>.pdf`) and `PresentButton` once a root exists. Present opens one popup, `/present?pdf=&role=presenter&channel=` (`features/latex/present/`, `app/present/page.tsx`): current and next slide, notes, n/N, timer. "Open audience window" opens the audience popup on the same `BroadcastChannel`, slide position syncs both ways. Notes are the PDF's `/Text` annotations, written by the theme's `pdfpc` `overridenote` (`\note{...}`, hidden, UTF-16). `PdfPageSlot` drops hidden and `/Text` annotations before react-pdf draws the annotation layer (`dropUnshownAnnotations`), links stay. The presenter keeps the PDF it opened with, a rebuild needs a reopen. **Embeds:** `SlideView` loads every link of the deck whose URL carries `embed=1` in an iframe as soon as the deck opens (`slideEmbeds.ts`, from the pages' link annotations), in both windows. A frame stays hidden until its slide shows, then it covers the link's rectangle and takes the keyboard, so changing to its slide needs no load. Every frame is told whether its slide shows (`postMessage({ type: "deck-shown", shown })`), so a hidden page can pause. The framed page holds the keyboard and hands unused keys back with `postMessage({ type: "deck-key", key })`, which run the deck's key handlers. Mirroring its own state between the presenter and the audience frame is the framed page's job. The app is served over HTTPS, so an embed needs an HTTPS URL.
- **Images.** A screenshot pasted into Neovim is stored on every Neovim surface (workbench, Code file panel, document editor) when the shown file is an absolute `.tex` or `.md` path. `"+p` and `p` read the browser clipboard (see Neovim sessions), and Ctrl+Shift+V of a lone PNG is intercepted at the terminal host. `useNeovimTerminal` owns both through `storeClipboardImage` (`features/editor/clipboardPaste.ts`): `POST /api/workbench/image?path=<shown file>` (multipart `file`) stores the PNG as `imgs/img-<YYYYMMDD-HHMMSS>.png` through `DiskFiles.create` (400 for a non-PNG signature, 413 above 20 MB, 409 when the name exists) and answers `{path, reference, changed}`. LaTeX stores in the project folder and references `\includegraphics[width=\linewidth]{imgs/img-….png}`, Markdown next to the file with `![](imgs/img-….png)`. A LaTeX root without `graphicx` gets `\usepackage{graphicx}` below its `\documentclass` (`latex.ensure_package`), recorded in `changed`. The `clipboard` answer is `reference` plus a newline (pasted linewise below the cursor), the paste event inserts it with `insert_lines` next to the buffer on screen (`shownPath`, the workbench's shown file, else the document path). `announceFileChange` runs for the image and each `changed` path, so a mount or promoted folder whose tree does not list the image yet reloads (`isNewFileIn`). Any other path (other file types, stored keys, relative paths) pastes no image and answers `error: "Images paste only into LaTeX or Markdown files on disk"`, a failed upload answers its reason ("Image is too large"), both shown as an error in Neovim (a paste event reports through a `message` frame).
- **Layout.** `WorkbenchFrame` (`features/workbench/WorkbenchFrame.tsx`) is the one layout of `Workbench` (Markdown, LaTeX) and `NotebookWorkbench`: Neovim's page (`editor`) and the rendered pane (`renderPane(layout)`, lined up through `usePaneLayout`) share the width, top and bottom edge, the chat drawer (`chat`) sits right. The rendered pane scrolls inside a box of the editor's height below the top bar, so `renderPane` gets `layout` with `top` and `bottom` 0. The owner holds the view (`useWorkbenchView` in `WorkbenchSplit.tsx`, with `show` to bring a hidden pane back), the frame keeps a hidden pane mounted and renders the view switch then `status` into the `workbenchStatus` slot, which sits in the middle of the top bar before the `center` slot. `editor: null` means no editor pane and no switch, the pane takes the width (the notebook with Neovim disabled). `Workbench` keeps its editor pane with Neovim disabled and shows `EditorNote` "Neovim is not enabled." there, `EditorNote` also shows "Loading…" and load errors. Its `renderPane` gets `WorkbenchPane {layout, text, loadError, editor}`, `editor` is `{reveal, send, focus}` (`WorkbenchEditorActions`, null without Neovim), the same actions reach the top bar's `center`. A workbench has one notice channel (`useWorkbenchNotice`, `ReportNotice(source, notice)`): the latest notice wins, a success clears only a notice of its own source.
- **Kinds.** `MarkdownWorkbench` renders `LaTeXMarkdown` from the synced text, tool artifacts filling the page. `LatexWorkbench` builds the project's root (not the shown file) on open, and on every change in the project folder through one queue (builds never overlap, bursts collapse) (`POST /api/latex/build`: latexmk in the root's folder, output in `.latex-build/`, last good PDF published atomically as `<stem>.<content hash>.view.pdf`, the newest three kept, so the range-loading viewer never reads a file replaced under it, 503 without latexmk). A build error names its file (`LatexIssue.file`) when it is not the shown one. `PdfViewer` swaps a rebuilt PDF in only after the new document drew the pages near the viewport, so it never blanks. A new kind is one wrapper around `Workbench` plus a prompt file and a `Kind` entry. The `pdf` kind has no wrapper: `prepare` resolves the PDF without moving it and `create` refuses it.
- **Primitives.** `DiskFiles` (`lib/disk_files.py`, provider `get_disk_files`) creates (`FileRoots.create`, exclusive, `FileExistsError` maps to 409) and overwrites files under the roots and records the `document` change keyed by the resolved path. Its `record` serves a writer that wrote already. `record_removed(paths)` records a `delete` change for each path a deleter removed. `FileRoots.ceiling_of(path)` is the file root holding the path, else the home folder when only host access reaches the path (host access is limited to home), else `ValueError`. `naming.segment(name, hidden=False)` is the one single-segment name check (`ValueError` for empty, separators, control characters, `.`, `..` and, unless `hidden`, a leading dot). Frontend: `lib/paths.ts` (`isInside`, `relativeIn`, `relativeTo`), `lib/backend/fileEvents.ts` (`announceFileMove`/`onFileMove`, `announceFileChange`/`onFileChange`) and `lib/domain/files.ts` `isNewFileIn`.
- **Limits.** A write made while the watch socket is down is picked up when it reconnects. Users sharing a project slug share its workbench folders. Moving to another backend host needs the same absolute `GIGACHAD_BASE_DIR` (references are absolute) and a copy of `~/.pi/agent/sessions` (sessions).
- **Follow primitive.** Every editor where the user writes text follows its file. Backend `WS /api/files/watch` (`routes/file_watch.py`, trusted origin from `backend/websocket_origin.py` plus login): `{type: "watch", files, folders}` replaces the socket's watch set, `{type: "changed", path}` and `{type: "refused", path, message}` come back. `lib/file_watch.py` watches files through their parent folder (atomic saves) and folders recursively with `watchfiles`, debounced 100 ms, without build output, `.git`, `node_modules` and editor scratch (`4913`, `*.swp`, `*.swo`, `*~`). Each watch blocks a thread the watcher starts itself (never anyio's shared pool of 40 that sync routes use), it ends within a polling step of a replaced set or a closed socket. Frontend `lib/backend/fileWatch.ts` keeps one lazy ref-counted socket per tab with backoff reconnect and a catch-up report of every watched path after a reconnect, every `changed` goes through `announceFileChange`. `hooks/useFollowFiles.ts` registers absolute paths and subscribes `onFileChange`. Adopters: the workbench (`useFollowBuffers`, `useLatexBuild`), `useRootFileDocument` (clean editors reload, Neovim ones merge through `onFollowed`), `FilePanel`, `TextDocumentEditor`, `useDiffNeovim`. Stored keys (`project/...`) are not on disk and keep their sync change events.

## Presentations

LaTeX decks built from a versioned template set. Rules for editing a set: `templates/latex/AGENTS.md`.

```
templates/latex/
├── AGENTS.md                         editing rules, re-render after every change
├── render.py                         primitives -> example.tex -> example.pdf -> previews (latexmk in a temp dir)
└── <set>/                            one template set, e.g. presentation
    ├── template.toml                 label, files copied into a new document, image macro, primitive groups (key, label) in order
    ├── beamertheme<set>.sty          theme, accent is one `\definecolor{accent}` line
    ├── skeleton.tex                  main.tex of a new presentation
    ├── STYLE.md                      agent style guide
    ├── primitives/<group>/<NN>-<name>.tex   one frame each, line 1 `% <Label>: <purpose>`
    ├── example.tex, example.pdf      generated from the primitives, committed
    └── previews/<group>/<NN>-<name>.png   generated, each primitive's last overlay page, committed
```

- **Structure.** Slide rules every theme shares (chapters, one claim per slide, bullets, sources, notes) live in the agent prompt [`templates/workbench/latex.md`](../templates/workbench/latex.md), each set's `STYLE.md` adds its own: [`presentation`](../templates/latex/presentation/STYLE.md) the primitives and their interface convention, [`draft`](../templates/latex/draft/STYLE.md) a plain theme for settling storyline and content, planned visuals as `\visual{}`, open points as `\question{}`. The theme is the agent's mode: on request it switches the root's `\usetheme`, copies the new set's `files` from the template-set folder, converts what the new theme does not define and announces the mode change. The chat is shared per folder, so naming another root of the folder in it makes that the agent's root.
- **Sets.** `lib/latex_templates.py` reads `config.TEMPLATES / \"latex\"` (`config.TEMPLATES` is the repo's `templates/`, frozen builds bundle it under `sys._MEIPASS`). `template_sets()` lists folders holding `template.toml` and `skeleton.tex` as `TemplateSet`s (cached per `template.toml` mtime, a malformed manifest, e.g. `files` naming a missing file, is logged and skipped), `template_set(name)` picks one. A set with `primitives/` is a presentation set (`is_presentation`), one without is a document set: `letter/` is a KOMA-Script `scrlttr2` DIN 5008 letter whose design lives in `layout.lco` and sender in `sender.lco`. `TemplateSet.primitives()` is re-read when a primitive file or preview changes. `GET /api/latex/template-sets` answers `[{name, label}]` for both kinds.
- **Detection.** A root is a presentation when its comment-stripped text has a `\usetheme[opts]{X}` naming a presentation set (`latex_templates.presentation_theme`, the first one wins). Nothing is toggled or stored.
- **Primitives.** `GET /api/latex/templates?root=` (resolved like `/project`) answers `{theme, primitives: [{id, group, group_label, label, description, summary, text, preview}]}`, `theme` null for a plain root. id `<group>/<name>`, ordered by the set's `groups` (unknown groups after them, alphabetically) then `NN`. `summary` is the description's first clause as plain text (LaTeX commands stripped). Malformed files are logged and skipped. `preview` is the mtime in ms of the primitive's preview PNG (null without one), `render.py` finds each primitive's page with SyncTeX on its `\end{frame}` line. `GET /api/latex/templates/{theme}/previews/{group}/{name}.png` serves it only for a known set and a primitive `primitives()` lists (404 otherwise, no path from the request reaches the disk), cached `private, max-age=31536000, immutable` since the frontend URL carries `?v=<preview>`.
- **Create.** `POST /api/workbench/create {slug, name, template}` with a known set (else 400, also for Markdown) writes the document folder through `TemplateSet.populate` (`main.tex` from the skeleton bytes, the set's `files` such as the theme `.sty` or `sender.lco`, an empty `imgs/`), lists the folder in the project and answers the `main.tex` path. `new_folder` removes the whole newly created tree when writing or listing fails. Each project owns its copies, so it builds on Overleaf as-is and may diverge. Frontend: the files folder's `+` asks for the file type (Markdown, LaTeX), then for LaTeX the template: "Blank" for a plain `.tex`, then every set under its label, loaded by `useWorkspaceDocuments` from `/api/latex/template-sets` (no template step when they fail to load). The follow-up window is `FileTreeCreateChoice.then` of `components/ui/file-tree/FileTree.tsx`.
- **Add slide.** `LatexWorkbench` loads the template set per root (a failed load counts as plain) and, with Neovim enabled, puts `AddSlide` (`components/ui/CommandPicker.tsx` over the primitives grouped by `group_label`) into the top bar's `center` slot. `CommandPicker` is the app's one search picker: the tab picker (`TabPicker`, a tapped Space outside text fields and controls, a Space held through a pointer press stays the canvas pan; while it is open Delete at the search's end or Alt+W closes the highlighted background tab, Alt+T opens a background tab and highlights it, the picker stays open and `TabManager`'s own Alt+W/Alt+T never fire) and the file and document pickers (`FileViewer`) use it too, both through `FloatingPicker`, which has no trigger. It shares the `PillPopover.tsx` shell with `PopoverSelector`, which stays selection only. The panel opens with its search field focused and one row highlighted, `initialKey` or the first, the first again after every filter change. Escape closes with focus back on the button. Rows show the primitive's label and `summary`, the filter matches label, group and summary. With `renderPreview` the picker is a finder and a preview in one: the page dims (`ModalBackdrop`, a click closes), the highlighted row shows in a pointer-transparent floating window (`FloatingPanel`) at `previewAspect`, centered on the window by `pickerLayout`, the finder a sidebar card (`SIDEBAR_CARD_CLASS`, `SidePanelScroll`) as tall as it on its left. The window's background is `AmbientCopy`: a video of the app background's canvas (`lib/ambientCanvas.ts`, set by `AmbientBackdrop`), shifted so it lines up with the background around the window, so no page content shows through. Clicks pass through the window to the dimmed page, a wheel over it scrolls its first vertically scrollable element (`firstScrollable`). Without a preview the list opens at its trigger. None shows while it returns null. The list is portaled out of the top bar (`PillPopover` `portal`). `AddSlide` fills it with the preview PNG and returns null without one or once it failed to load. A pick sends `{type: \"insert_frame\", text}` through `editor.send`. `NeovimSession.insert_frame` reads `_G.gigachad_cursor_state` (lines, cursor row, buffer, `changedtick`), `tex_source.frame_insertion` places the frame after the `\end{frame}` of the frame around the cursor, below the cursor outside a frame, before `\end{document}` from the preamble or after `\end{document}` (comments ignored), and `_G.gigachad_insert_at` applies it only if the same buffer still shows with the same `changedtick`. A changed buffer is retried once, then the failure is logged. The cursor lands on the new `\begin{frame}` line. Templates load once per root: a `\usetheme` added by hand shows the button after the workbench reopens.
- **Insertion point.** The insertion point is Neovim's cursor, there is no second mechanism. With Neovim enabled, a presentation root's PDF pane makes the gap between two pages clickable: `LatexPdfPane` renders it through `PdfViewer`'s `renderPageOverlay(page, width, pageCount)`. A click goes through the slide gap hook of `useSynctex.ts` to `POST /api/latex/synctex/slide {path: root, page}` for the page above. `synctex.slide_end` reads that page's records from `<stem>.synctex.gz` itself, keeps those in `.tex` files of the root's folder (no `.toc`, theme or texmf files), resolves each to the `\end{frame}` of its frame (`tex_source.frame_end`) and takes the most frequent `\end{frame}` line. A page without one is a theme's chapter slide, attributed to its `\section` line, which moves past the deeper headings right below it (`\subsection`), so the new slide belongs to that subsection. 404 without a slide, 403 for a file outside the mounts. The answer goes to `editor.reveal` without showing or focusing Neovim, then the line stays in that gap (`marked`). The next \"Add slide\" (`onInsert` returned true), another gap or Escape in the PDF pane clears it, a failed lookup shows a notice in the top bar.
- **Images.** Primitive image slots hold mwe placeholders (`example-image`, `example-image-16x9`, ...). For a presentation root `/api/workbench/image` references the image with `TemplateSet.image_reference` (the set's image macro, `\roundimage{imgs/<file>}`) and skips `graphicx` (beamer loads it), `StoredImage.placeholder_path` is `imgs/<file>`. Ctrl+Shift+V sends `{type: \"insert_image\", path: placeholder_path, reference}`: `tex_source.fill_placeholder` puts `path` literally into the first placeholder of the cursor line (`_G.gigachad_set_line`), else `reference` goes below the cursor (`_G.gigachad_insert_at`), under the same buffer and `changedtick` check and single retry as a slide. Neovim's `p` still pastes the reference.
- **Agent.** The agent reads the sets where they ship: `templates/workbench/latex.md` names them by absolute path (`{{TEMPLATES}}`, `latex_templates.TEMPLATE_SETS`), gives the shared slide rules and sends the agent to `<templates>/latex/<X>/STYLE.md` of the root's `\usetheme{X}`. The `draft` set has no `primitives/`, so the app treats a draft root as plain LaTeX (no Add slide, no slide gap, `\includegraphics` for pasted images), the agent still gets its `STYLE.md`.

## Memory and deletion semantics

| Memory stage | Contract |
| --- | --- |
| Scope | Document-backed JSON, not vector search. Atomic memories (`{id, text, topic, scope, ...}`) belong to topics (`{name, summary}`), the complete memories. A `MemoryScope(kind, slug)` names the global profile or one project. Global: `memory/global-topics.json` + `global-profile.json`, seeded with `profile` and `preferences`. Project: `memory/project/<slug>/memory/topics.json` + `memory.json`, no seed topics. Persistence lives in `memory_store.py`, LLM extraction/regroup in `memory_extract.py` (`MemoryExtractor`), prompt injection in `memory_context.py`. |
| Extract | Manual (`/memorize`, Alt+M), using the stored `memory_model`. Always the global scope, plus the project scope when the conversation has a project. A chat sends its messages. A Pi tab sends the open session's confirmed prompts and replies (user and assistant text only, no thinking, tool calls or notices), the session id keying the watermark. One call per scope after its `(chat_id, scope)` watermark returns operations (`add`, `update`/`delete` by short fact id) plus summaries for new or outgrown topics. `build_proposal` drops unknown ids, repeated targets, duplicates and no-ops, and gives every new topic a proposal. |
| Review | One screen (`MemoryPanel`): accept, edit, move or deny each operation, rename or summarize new topics (renaming onto an existing topic merges), accept or deny summary revisions. |
| Commit / cancel | `POST /api/memory/commit` applies accepted operations deterministically (stale targets skipped), upserts topics, then advances that scope's watermark, also when every operation was denied. Topics, memories, watermark and pending buffer are written in one `DataStore.apply` transaction. Cancellation discards the review without advancing. |
| Injection | `memory_context.augment_system_prompt` renders every fact of the global scope and, in a project, of its scope under `Persistent Memory Context`, as `- [Topic] text` in stored order. Stored order is the relevance order, index 0 first, there is no budget or pinned topic. The extraction prompt lists facts in that order (`m<N>` is 1-based position N), the model may give `position` on add and update, `build_proposal` turns it into `MemoryOperation.index` (0-based, no-op moves dropped) and `MemoryStore.commit` places the fact there, appending when absent or past the end. Manual adds append, the memory window's relevance page (`RankingPage`, `shiftMemory`) swaps neighbours and saves the whole list. |
| Maintenance | One memory window (sidebar brain button, `features/memory/MemoryViewer.tsx`) lists global and per-project topics. Every edit writes immediately (`PUT /api/memory/topics`, then `PUT /api/memory/memories`), queued per scope. Facts move between topics, a title naming another topic merges into it after confirmation. `POST /api/memory/regroup` proposes subject topics for a scope, applied only after review. Deleting a topic deletes its memories, undoable via `UndoDeleteContext`. |

- Use `UndoDeleteContext` for deferred resource deletions. Scheduling the next deletion commits the previous one, refusal restores it. Leaving the page (`pagehide`, or the document turning hidden) commits the pending deletion instead of dropping it with the timer, and `DELETE` requests use `keepalive` so they still reach the backend during unload.
- A committed project file delete is live everywhere. `DELETE /api/documents` answers `removed`, the keys and absolute paths that are gone (a mounted file only unlinked stays out), and records a `delete` change for each absolute one (stored keys record their own). `useWorkspaceDocuments` calls `announceFileRemoval(path)` for each (`lib/backend/fileEvents.ts`, its listeners never get this device's own change events) and other devices reach the same `onFileRemoval` listeners through the `delete` event. The shared lists drop the entries at or inside the path for every tab at once (`watchDocumentLists`, a list reads again when the path lay in one of its folder entries). `TabManager` closes every tab whose file item lies inside the path or whose workbench `texFolder` does (`tabsAfterRemoval`), the frontmost one passes to the nearest tab before it and the last tab becomes a fresh chat, a workbench tab's Neovim session ends with it. Nothing prunes tabs on reload, tabs are not stored.
- A tab's crumb names the project its item belongs to (`tab.projectSlug`). The sidebar opens the files of a folder on disk with `owningProject` (`workspaceTree.ts`): the project listing the path as an entry or inside a folder entry, else the project whose linked folder holds it, else none.
- Remove chat pairs/attachments from model context immediately while allowing undo. Undo restores by message identity: a pair goes back before the message that followed it (at the end once that is gone), an attachment only into the message it was removed from. Keep canvas history independent.

### Delete cleanup

`lib/references.py` is the one reference model. Every delete path records what it let go of in a `Released` (`owned` keys it deletes itself, released `refs`, deleted `chats`), commits its own delete, and only then calls `References.release`, so a failed delete never loses shared data.

| Delete | Removes | Unless |
| --- | --- | --- |
| Chat, cascade, merge child (`ChatCleanup.after`) | Its uploads and sidecars, sandbox state, then the library PDF and annotation canvas of each PDF it referenced | Another chat, project, held canvas or upload still references the PDF name (library) or the bytes (annotation) |
| Project (`ProjectStore.delete_project`) | Its chats as above, its stored documents `project/<slug>/document/...` (canvases release what they show) and what its files derived | Another project lists the document, a chat or held canvas references it |
| Project file (`DELETE /api/documents`) | The reference, then the file and its derived data. A workbench document folder `WORKBENCH/<kind>/<slug>/<folder>` is app-created: its whole folder and chat links go (irreversible on disk, undo only before the deferred delete fires), and the slug folder with it when that was its last | As for a project. A note (empty slug) is deleted outright, its derived data released. A mounted file or folder is only unlinked, never deleted |
| One chat upload (`DELETE /api/files/chat/...`) | The upload and its sidecar, then its library copy and annotations | As for a chat |
| Canvas | Its mutation log and share rows (foreign keys `ON DELETE CASCADE`), annotation canvases included | |

- Held canvases: every `note/` canvas, and project canvases a chat, a project's `files` or another held canvas reaches. Annotation canvases count PDF bytes: stored uploads, library PDFs and document PDFs, plus host PDFs a chat, project or held canvas references, hashed from disk.
- Annotation canvases of host PDFs opened from the file tree: `POST /api/fileviewer/annotations` records each resolved host path in the canvas's meta `hosts` (`annotation_canvas`, kept by `CanvasMutationStore` across batches). The canvas stays while any recorded file still exists with its hash. Cleanup stats a recorded file and hashes it only when nothing stored keeps the canvas.
- MinerU output (`Mineru/<stem>.md`, `Mineru/images/<stem>/...`) is never deleted by a release nor listed by the dry run.
- Host files are references only: hashed, never written or deleted. The PDF/MinerU convenience mirror on disk is left alone.
- Cleanup failures after the commit are logged, not raised. Nothing purges older orphans automatically: `python -m lib.references --dry-run [--database-url URL]` (from `src/`) lists them per user with sizes, plus uploads of chats that are not stored. Its reads may store missing meta, never content.
- Pi sessions: gigachad-bot stores nothing per session, Pi keeps them in `~/.pi/agent/sessions`. A Pi composer's uploads are keyed by its draft key (`pi:<session>`) and show up in the dry-run report once no stored chat has that ID.

## Provider usage

- Serve `GET /api/provider-usage` from `omp usage --json` through `lib/provider_usage.py`. Cache for five minutes, invalidate OMP's cache first for `?refresh=true`.
- Return 502 for missing/failing OMP. Reuse last reports for dropped providers for up to an hour, adjusting reset times. Report unavailable accounts without retained reports explicitly.
- Summarize five-hour limits and expose other provider windows. Never substitute weekly values for missing five-hour limits.

## Production redeploy

- `POST /api/deploy/redeploy` (host access, settings menu) starts `redeploy.sh` as transient user unit `gigachad-bot-redeploy` via `systemd-run`, so restarting the backend does not kill it. Returns 202, or 409 with stderr while one runs or when the start fails.
- The script rebases the production worktree onto `origin/master`, refusing tracked changes, restarts pi-host when `pi-host/` or the installed Pi changed (never while a Pi session runs a turn), then restarts `gigachad-bot.service` from a clean environment, then learn mode and the preview gate. Remotes fetch over HTTPS: the unit has no SSH agent. Steps and rollback: [deployment](deployment.md).
